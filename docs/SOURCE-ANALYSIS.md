## Що насправді робить SDS

Оригінал не пише новий safety data sheet. Він копіює існуючий PDF із 41 сторінки: paint SDS (23 сторінки) і varnish SDS (18 сторінок), змінює верхню назву на сторінках 1–23 і додаткову назву у розділі 1.1 першої сторінки — разом 24 області. Решта змісту має лишатися незмінною.

Координати зон, базові лінії тексту, placeholder-и, іменування PDF, чотири дати еталона й перевірки витягнуті з `sds_core`. Порт перевіряє слова поза зміненими областями на **всіх 41 сторінках**, число назв та збереження кількості `Clear varnish`. Він не видаляє блоки небезпек, речовини чи поради щодо захисту. Назва файлу `_repaired_no_filter_mask` успадкована з оригіналу й не означає, що вебсервіс робить нові подібні правки.

Власний еталон має відповідати цій структурі. Для іншого документа є окремий PDF-редактор, а не довільна підстановка у фіксовані координати.

## Практичні рішення

- Python збережений, щоб не переписувати перевірений колірний алгоритм на JavaScript і не змінювати результат.
- UI — статичний Vite build; SSR для двох внутрішніх інструментів не потрібний.
- Без бази даних і постійного worker: пакет виконується, поки відкрита вкладка. Серверна історія завершених результатів — окремі JSON-manifest і копії файлів у S3/R2 на 30 днів. Клієнт передає спільний UUID `batch_id`, індекс, заплановану кількість, ZIP-шлях та ISO LastWriteTime. Частковий пакет зберігає завершені результати; сторінка історії і ZIP працюють із цілим пакетом. Старі записи без явного ID залишаються окремими: надійного способу відновити їхні початкові списки немає. Фонові пакети та відновлення незавершених задач не реалізовані; для них потрібна черга.
- Immutable membership-файли містять накопичувальний summary snapshot: за звичайної послідовної генерації історія читає один summary на пакет замість до 200 manifest. Точна перевірка всіх member IDs захищає від застарілої/конкурентної версії; fallback читає оригінальні manifest. Для деталей/fallback максимум 8 паралельних S3 GET, без спільного змінюваного лічильника. Контракти і fallback перевірені тестами, latency у живому bucket не виміряна.
- S3/R2 обов’язковий на Vercel, оскільки реальні шаблони 4,8–6,4 МБ перевищують ліміт HTTP payload функції. Генераційні запити передають JSON-метадані, відповіді — metadata/посилання; бінарні файли не передаються в base64.
- Видалення builtin PDF/машин — прапорці у preferences, а не стирання packaged assets; відновлення доступне окремими API. Власні durable PNG/маски/PDF видаляються фізично лише в `library/files/`. Історичні результати — незалежні копії, тому не зникають після видалення джерела.
- LastWriteTime не змінює серверний `mtime`: давня вибрана дата не робить новий результат простроченим. У ZIP записується київський wall-clock час, а у JSON-звіті — ISO instant і `Europe/Kyiv`; 2-секундна DOS-точність відрізняється від точності ISO.
- Без hard-coded Windows-шрифтів; Noto Sans включено з ліцензією OFL. Текст може переноситися трохи інакше, ніж у desktop; його повнота перевіряється після збереження.
- MuPDF/важка обробка серіалізована всередині процесу: уникнення thread-safety проблем і зайвого пікового використання RAM.

## Що не підтверджено

Візуальна перевірка сторінки 9 виявила обрізаний правим краєм основний текст. Порівняння растрової області нижче заголовка з вихідним `reference.pdf` дало повну піксельну рівність: дефект належить еталону, не новому генератору. Він задокументований, але сам еталон не переписувався.

Реальний cold start, час/пам’ять Vercel, живий S3/R2, CORS домену, login на production і скачування великого файлу з хмари не перевірені без підключеного облікового запису та bucket. S3-контракти перевірені boto3 Stubber без зовнішньої мережі; локальний backend має 40 успішних тестів станом на 04.10.2026. Це і статична конфігурація не видаються за успішний деплой.
