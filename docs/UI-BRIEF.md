# ТЗ на розвиток мінімалістичного UI Content Workshop

## Контекст і межі

Сервіс об’єднує HexPh (перефарбування товарних PNG) та SDS (заміна назв у готовому SDS і пошук/заміна тексту PDF). Фронтенд: React + TypeScript + Vite. Поточна оболонка — `frontend/src/App.tsx`, styles — `frontend/src/minimal.css` і `frontend/src/theme-transition.css`; контракти — `docs/API.md`. Старі `styles.css` і `settings.css` не є основою нового дизайну.

Чинний напрям: радикальний Apple-inspired мінімалізм, темно-сірий + білий, рівноцінні темна й світла теми, плавний центральний перемикач «Фото / SDS». Попередній скляний напрям більше неактуальний. Прибирати зайві пояснення й рамки, але не потрібні функції, помилки або доступні назви контролів. Не додавати фіктивні графіки, облікові записи, показники економії, DOCX-експорт чи генерацію хімічного складу. SDS не створює паспорт безпеки з нуля.

## Візуальний напрям

- Темна тема: фон `#191919`, поверхні `#242424`, текст/головна дія `#f5f5f5`. Світла: фон `#f5f5f5`, поверхні `#ffffff`, текст `#191919`, головна дія `#242424`. Другорядний текст і рамки — відповідні theme tokens, не механічний CSS invert.
- Стриманий синій акцент `#3768b0` тільки для фокусу, посилань і вибраного стану. Без неону, glow, декоративних градієнтів, backdrop blur і великих кольорових поверхонь. Реальні кольори PNG/swatches не змінювати під тему.
- Системний font stack із `minimal.css`; без додаткового завантаження шрифтів. Компактна типографіка: основний текст 13 px, заголовки панелей 14 px, підказки 11–12 px. Не зменшувати текст для боротьби зі скролом: спочатку прибирати дублювання й групувати параметри.
- Матова поверхня форми, тонкі нейтральні межі, радіус приблизно 8–12 px. Усередині форми не створювати вкладені картки для кожного поля. Видимий focus і відмінні `hover/disabled/loading` в обох темах.
- Перемикач режиму: ковзання thumb приблизно 330 ms; зміна робочої області — коротка поява/зникнення 190–280 ms з мінімальним зсувом. Без затримки доступу до нового інструмента, різкого стрибка макета й нескінченних декоративних анімацій. `prefers-reduced-motion` вимикає рух.
- Тема: кругова хвиля від toggle до протилежного кута, 620 ms через View Transitions; fallback fade без підтримки API, immediate при reduced motion. Форми й PNG/PDF не перефарбовувати фільтрами.

## Інформаційна архітектура

Одна компактна sticky-шапка: назва сервісу ліворуч, «Фото / SDS» по центру, іконки історії, налаштувань, теми й умовного виходу праворуч. Без sidebar, breadcrumb, hero, рекламних тез і постійного дублювання назви інструмента. Іконки мають `aria-label` і короткий tooltip. Повторне натискання відкритої історії/налаштувань повертає до попереднього робочого режиму.

Desktop: одна форма ліворуч, великий справжній preview/результат праворуч. Головна дія закріплена знизу форми. Фото: шаблон → кольори → «Створити PNG»; маски/номер розкриваються за потреби. Експорт — окрема двоколонкова панель, що з LastWriteTime вміщується на 1280×720; на низьких екранах прокручується лише body, не footer. SDS: джерело → режим назв → товари → «Створити SDS»; шаблон назви, зміна еталона й перевірені назви — компактні disclosure-блоки.

На вузькому екрані форма й preview складаються в одну колонку; поточний breakpoint — 700 px. На ширшому планшеті дві колонки допустимі лише за читабельних контролів. Перевіряти 360 px і крайній 320 px; жодного горизонтального скролу сторінки. Адаптація шапки не має приховувати перемикач або утиліти.

Зберегти введені дані й результати при перемиканні режимів/теми; не remount-ити інструменти. Неактивні області недоступні для фокусу та screen reader. Модальний редактор має бути поза анімованими/transformed областями, блокувати фон, замикати фокус і повертати його після закриття. Тема запам’ятовується локально; це не замінює серверного зберігання бібліотеки й історії.

## HEX → PNG: функціональні вимоги

1. Джерело: готовий шаблон з API або власний PNG. Показувати назву і розміри; не підміняти шаблон декоративним зображенням.
2. Маски кузова та маркера: ознака наявності, завантаження PNG, редактор пензлем/гумкою. Виділення номерного знака прямокутником у координатах оригіналу. Chroma-маска з ключового HEX.
3. Палітра: багаторядковий `КОД HEX [metallic]`, імпорт CSV. Показ перевірених swatches і конкретних помилок рядків із сервера. Порожній список не може запустити генерацію.
4. Налаштування: бренд, модель, lightness `match/keep`; додатково feather, font size, назви/папки у ZIP, імпорт конфігурації JSON.
5. Дії: перевірка перших двох кольорів; весь батч; зупинка після поточного файлу. Прогрес відповідає фактично завершеним файлам.
6. Результати: вкладки по кодах, справжні PNG-прев’ю, ΔE із сервера, окреме скачування та ZIP зі звітом `generation-report.json`. Завершені файли зберігаються при помилці/скасуванні решти батчу. Після зміни налаштувань попередні результати залишаються доступними з явною позначкою «файли попереднього запуску».
7. LastWriteTime у Фото та SDS: початок у `Europe/Kyiv`, хвилинний крок/діапазон, план дат один раз перед запуском; ISO-дата зберігається на сервері та у звіті. ZIP-entry має київський wall-clock час із DOS precision 2 секунди; окремий датований файл теж у ZIP. Не обіцяти OS mtime для прямого download.

## SDS Studio: функціональні вимоги

У режимі SDS два локальні варіанти: «Генерація» та «Заміна тексту». Вони не конкурують з головним перемикачем «Фото / SDS».

Генератор: посилання на реальний 41-сторінковий PDF із налаштувань; можливість тимчасово завантажити інший сумісний еталон до 25 MiB і повернути типовий. Власний еталон повинен мати структуру початкового SDS; сервер перевіряє її при генерації, а постійний еталон — ще до збереження в налаштуваннях. UI перевіряє розмір, розширення і заголовок PDF, але не називає структуру перевіреною до відповіді сервера. Режим шаблону з `{VALUE}`, `{CODE}`, `{COLOR}`, `{BRAND}` або точні записи `CODE | BRAND | COLOR | TITLE`; `BRAND` тут означає марку автомобіля. Попередня перевірка готових назв і назв файлів; послідовна генерація PDF, прогрес і скасування. Прев’ю першої сторінки, кількість сторінок і результат серверної валідації; скачування PDF/ZIP зі звітом генерації.

Редактор: завантаження PDF; текст пошуку/заміни; сторінки `all` або `1,3-5`; урахування регістру й усі збіги. Спочатку пошук і список реальних збігів, потім застосування. При зміні параметрів пошуку попередні збіги скидаються. Готовий PDF залишається доступним для завантаження з поміткою про попередні налаштування.

## Стани, які обов’язково відмалювати

Налаштування: типова назва SDS з токенами `{BRAND}/{VALUE}/{CODE}/{COLOR}`; поточний PDF-еталон, upload/валідація/видалення/відновлення; розкривна форма додавання машини з PNG, необов’язковими масками й HEX; галерея вбудованих і власних машин. HEX зберігається окремо для кожної машини та підставляється при її виборі. Збереження — явною кнопкою; success/error помітні поруч із робочою областю. Усі машини можна видалити: builtin приховується й відновлюється з окремого списку, власні PNG/маски фізично видаляються лише після підтвердження незворотності. Історичні результати лишаються. Діалоги — власні accessible modal, не `window.confirm`. Без PDF явно показати відсутність джерела й блокувати генерацію, не повертати builtin приховано. Картки мають обмежену область image без перекриття назви/HEX/кнопок. Налаштування та бібліотека зберігаються на сервері без 30-денного TTL. Оновлювати каталог/defaults без reload, не скидати індивідуальні правки іншого інструмента.

Історія: один запуск — один пакет зі спільним `batch_id`, серверне збереження на 30 днів. Список із кількістю/типом/датою, preview членів і кнопка «Завантажити пакет · ZIP»; при скасуванні лише фактично завершені файли. Пошук за всіма назвами/кодами завантажених пакетів, фільтр, пагінація пакетами; повторне скачування з датами після reload. Старі записи без ID лишаються окремими — не вгадувати групи за датою. Відверто показувати строк зберігання й межі пошуку. Без localStorage-імітації архіву.

- Порожній інструмент до вибору файлу.
- Завантаження файлу, аналіз списку, генерація окремого результату, формування ZIP.
- Некоректний формат, завеликий файл, помилка HEX/рядка, помилка сервера/мережі.
- Частково завершений батч, скасований батч, повністю завершений батч.
- Авторизація паролем, неправильний пароль, недоступне сховище.
- Немає збігів PDF, знайдено багато збігів, готовий PDF.
- Застарілі результати після зміни параметрів або PDF-еталона залишаються доступними для завантаження, але не можуть виглядати прев’ю нових параметрів.

Не вигадувати відсоток готовності всередині одного серверного запиту. Для такого стану потрібен indeterminate spinner. Для батчу показувати `завершено / всього`.

## Межі API, які дизайн не змінює

- До 25 MiB на upload, PNG до 8 млн пікселів, до 200 товарів/кольорів у пакеті, до 100 власних машин. Маски мають розмір вихідного PNG; потрібна маска кузова або ключовий HEX.
- Один результат на серверний запит; пакет послідовно виконує браузер, вкладку треба залишати відкритою. Зупинка діє після поточного запиту, а не миттєво на сервері.
- ZIP збирається у браузері до сумарних 250 MiB, понад це — окремі файли. Короткочасні download URL оновлюються через існуючий API; історія видає нові посилання на збережені результати протягом 30 днів.
- Один власник і спільна бібліотека, без багатокористувацького контролю версій. Зміна дизайну не означає готовий деплой або перевірену живу S3/R2-інтеграцію.

## Поліпшення наступної ітерації

Пріоритет 1: перевірити фокус/keyboard-only flow, назви іконок, контраст обох тем і touch targets; зберегти focus trap та повернення фокусу. Для основних touch-дій ціль 40–44 px; не вважати наявні компактні контролі автоматично перевіреними. Локальна валідація біля поля, видимий зв’язок форми з preview; помилка не знищує дані чи готові файли. Повний accessibility audit ще є окремою перевіркою, не заявою цього ТЗ.

Пріоритет 2: точково поліпшити поточні disclosure-блоки, легенду масок, адаптацію toolbar редактора та щільність налаштувань. Не переносити рідкі параметри на головний екран і не додавати нові взаємодії до суто стильової ітерації.

Пріоритет 3: лише після окремого погодження — нова UX-функціональність для великих батчів, додаткових PDF-прев’ю чи табличного вводу. Це не обов’язковий обсяг поточного redesign і не привід переписувати пайплайни.

## Критерії приймання

- Обидва інструменти працюють через існуючі API, жодних mocked success або демонстраційних результатів.
- Темна й світла теми мають рівноцінну читабельність; центральний перемикач та перехід областей плавні, reduced motion підтримується. Немає sidebar, breadcrumb, неону або декоративного скла.
- Перевірити viewport 360, 768, 1280 і 1600 px в обох темах; додатково крайній 320 px, зокрема шапку з кнопкою виходу. Без обрізаних контролів/горизонтального скролу.
- Основна дія доступна без зайвого скролу в звичайному desktop-сценарії; рідкі параметри розкриваються за потреби. Перемикання «Фото / SDS», утиліт і теми не губить введені дані/результати.
- Keyboard-only користувач може увійти, заповнити форму, запустити генерацію, завантажити файл і закрити модальне вікно.
- Кнопки мають однозначні `hover/focus/disabled/loading`, помилки оголошуються через `role=alert`, статус через `aria-live`.
- Screenshot review обох тем: порожній стан Фото, обраний шаблон, результат батчу, canvas редактор, генератор SDS, заміна тексту, налаштування, історія, mobile та login.
- `npm run build` у `frontend/` проходить; перевірено реальну генерацію PNG і PDF із завантаженням результатів.

Критерії — чекліст наступної ітерації, не підтвердження вже пройденого комплексного аудиту. Виконані перевірки й обмеження фіксувати окремо в `docs/VERIFICATION.md`.
